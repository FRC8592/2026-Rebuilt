## Repository layout

FRC Team 8592's code for the 2026 game (REBUILT). This repo is the frozen record of the 2026 robot, and it is also where planning for 2026 and 2027 happens (issues and project board #2). 2027 code will go in a separate repo, `FRC8592/2027-preseason`. That repo doesn't exist yet; #177 creates it.

**Only `robot-production/` is live.** It is the 2026 competition robot. Start there. It is the only tree with AdvantageKit, PhotonVision, PathPlanner, Phoenix 6 and the gversion plugin, and the only one CI builds.

**Six trees are abandoned, and their code looks current but will mislead you:** `Swerve`, `Swerve-Bunnybot`, `robot-chassis-A`, `robot-swerve-A`, `Bunnybot` (still on WPILib **2025**, GradleRIO 2025.3.2) and `robot-rebuilt`. The last real development in them was 2026-03-22. An Oct 11 commit changed only PathPlanner files in `Swerve` and `robot-rebuilt`. Their code differs from `robot-production`. For example, `robot-rebuilt` has an `atan` vs `atan2` bug, and some pose-estimation code exists only in `robot-rebuilt` and `Bunnybot`. **Before you act on a claim about "the code", confirm which tree it refers to.** #198 covers archiving these trees. Update this file when that lands.

Other top-level items:
- `Photonvision/` is not code. It holds PhotonVision camera calibration JSON exports, and nothing uses them right now.
- **There is no root gradle project.** The root has no `build.gradle`, `settings.gradle` or `gradlew`. Run `./gradlew` from `robot-production/`; CI does the same.
- The root `vendordeps/` is a leftover from 2024 and belongs to no gradle project (`REVLib` 2024.2.4 / `frcYear 2024`, `WPILibNewCommands` `frcYear 2025`). Never take a version from it. #198 removes it. The real vendordeps are in `robot-production/vendordeps/`.

**Current versions (robot-production):** GradleRIO **2026.2.1** (`build.gradle:3`), `frcYear 2026` (`settings.gradle:7`), Gradle 8.11 wrapper. Java 17 is declared through `sourceCompatibility`/`targetCompatibility`; there is no toolchain block, so the JDK comes from the WPILib 2026 install.

## Commands

Run these from `robot-production/`.

```bash
./gradlew build                 # compile + test (what CI runs)
./gradlew test                  # run tests (src/test does not exist yet)
./gradlew test --tests 'frc.robot.SomeTest'   # run a single test class
./gradlew simulateJava          # desktop sim with sim GUI + driver station
./gradlew deploy                # deploy to the roboRIO (team 8592 from .wpilib/wpilib_preferences.json)
AKIT_LOG_PATH=/path/to/log.wpilog ./gradlew simulateJava   # AdvantageKit replay
```

CI (`.github/workflows/gradle.yml`) runs `./gradlew build` in `robot-production` on pushes and PRs to `main`.

`BuildConstants.java` is generated by the gversion plugin before every compile and is gitignored. Don't edit it or commit it.

## Architecture (robot-production)

Command-based WPILib Java, package `frc.robot`. It uses AdvantageKit (`LoggedRobot`), CTRE Phoenix 6 swerve, REV Spark Flex, PathPlanner and PhotonVision.

- **`Robot.java`**: sets up AdvantageKit logging. On the real robot it writes WPILOG to USB and publishes NT4. In sim it writes logs locally, or replays a log when `AKIT_LOG_PATH` is set. It also handles the mode lifecycle and the match-time countdown written to SmartDashboard (`AutoTime`/`TelopTime`). `disabledPeriodic` does real work every loop: it calls `periodic()` on all three `Vision` instances by hand, drives the "tags seen" LEDs, passes the alliance to `Scoring`, and reloads shooter PID from SmartDashboard.
- **`RobotContainer.java`**: builds every subsystem and holds all controller bindings. The driver is on port 0 and the operator on port 1. It also registers the PathPlanner `NamedCommands` and `EventTrigger`s, then calls `AutoManager.prepare()`. The `commands/autonomous/AutoCommands` class duplicates that registration but is not called. The live registration is in `RobotContainer`. Default commands go through `setDefaultCommand()`, which rejects commands that aren't `kCancelSelf`.
- **`Scoring`** is the parent subsystem of the scoring mechanisms. It owns `Turret`, `Shooter`, `Indexer` and `Intake` as public fields, and callers reach them as `scoring.indexer.runIndexerCommand()`. It also gets `Swerve` (for pose and velocity) and `LEDs`. Its `periodic()` runs target tracking: `getTarget()` picks the alliance hub or a passing target from the robot's field position, then sets turret angle and shooter speed. That includes the shoot-on-the-move math (`SOTM`, `solveV0y`), plus operator RPM and turret offsets. Tracking is a toggle (`toggleTrackingCommand`). Manual override holds the turret and uses fixed shooter speeds.
- **Swerve** (`subsystems/swerve/`): `TunerConstants` and `CommandSwerveDrivetrain` are the CTRE Tuner X generated code. `Swerve` wraps them with joystick processing, slow modes, robot-relative mode, heading lock (`driveAtHeading`) and SysId. `AutoBuilder.configure(...)` for PathPlanner is called in the `Swerve` constructor.
- **Vision**: there are three PhotonVision cameras (back, left, right), each a `Vision` instance with its own `OdometryUpdates` subsystem. `OdometryUpdates` filters pose estimates and feeds them into swerve odometry.
- **Autos**: PathPlanner `.auto`/`.path` files live in `src/main/deploy/pathplanner/`. `AutoManager` builds the chooser from those files and adds some autos built in code (mirrored paths, double-swipe sequences). It puts an "Auto Delay" before the selected auto.
- **Motor helpers** (`helpers/TalonFXControl`, `helpers/SparkFlexControl`): these wrap the vendor motor APIs (PID slots, current limits, `motorLogging(logPath)`). Subsystems use these wrappers, not the raw TalonFX or SparkFlex objects. `examples/` shows how to use them.
- **`commands/proxies/`**: command wrappers (multi-composable, override-everything, timing-simulated).

## Conventions

- All constants go in `Constants.java` as nested ALL-CAPS classes, one per subsystem (`SHOOTER`, `TURRET`, `INDEXER`, ...). That includes CAN IDs, PID gains and current limits.
- Each constants class has a `LOG_PATH` built from `SHARED.LOG_FOLDER` (`"CustomLogs"`). Log with `Logger.recordOutput(X.LOG_PATH + "Name", value)`. Values for drivers and operators go to the Elastic dashboard through `SmartDashboard`.
- Subsystems expose `fooCommand()` factories, usually `this.runOnce(...)`, next to plain `foo()` methods.
- Branches are named `XX/<issue#>-<slug>`, where `XX` is your initials (e.g. `BS/169-github_actions`). Each PR into `main` is for one GitHub issue.
- Tickets use six headings, in order: What needs to happen / Why / Definition of done / How we'll test it / Where to start / Blocked by. When #215 adds `CONTRIBUTING.md`, replace these two bullets with a link to it.
- `.hoot`, `.wpilog` and `.revlog` files from matches are sometimes committed under `robot-production/`. They are data, not code.
